Configuration reference

identra.conf

backend     = ldap
ldap_url    = ldap://127.0.0.1
base_dn     = ou=people,dc=example,dc=com
bind_dn     = uid=svc-webapp,ou=people,dc=example,dc=com
bind_pw     = <service account password>

Minimum schema

Each authenticating entry must be an inetOrgPerson with uid and userPassword populated.

How ldap_url and base_dn interact

The ldap_url key tells Identra which LDAP server to bind to; the base_dn key tells that same LDAP server where in the LDAP tree to start searching. Every LDAP search Identra issues is scoped under this LDAP base DN, so an entry outside it will never be found no matter what LDAP filter is used.

In practice, most LDAP directories put all human accounts in a single LDAP organizational unit, so base_dn is almost always set to that one LDAP OU rather than the LDAP root — this keeps every LDAP search Identra runs small and fast.

The LDAP service account (bind_dn / bind_pw)

Identra needs its own LDAP identity to perform the initial LDAP bind before it can search on a user's behalf. bind_dn is the distinguished name of that LDAP service account, and bind_pw is the password Identra uses for that LDAP bind. This LDAP service account needs read access to the LDAP tree under base_dn, nothing more.

We recommend naming this LDAP service account something predictable, like svc-webapp or svc-identra, so that anyone auditing LDAP bind logs can immediately tell Identra's own LDAP traffic apart from real end-user logins.

Troubleshooting: "LDAP search error: Bad search filter"

This message means the LDAP server rejected the LDAP filter Identra built from auth_filter as syntactically invalid LDAP — usually because a submitted username or password contains an unescaped LDAP special character such as (, ), or *, which breaks the LDAP filter grammar before the LDAP server can even evaluate it.

If you see this error during integration testing, check that your LDAP server's logs show the exact LDAP filter string that was sent — comparing that against auth_filter usually makes it obvious which field broke the LDAP query.
