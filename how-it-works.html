How Identra SSO works

Three steps from login page to authenticated session.

1

Your app embeds the Identra login screen

Your existing login page posts the submitted username and password to Identra's auth endpoint instead of handling credentials itself.

2

Identra connects to your organization's LDAP directory

Identra binds to your directory using a dedicated service account, then runs a search filter built from the submitted credentials to locate a matching directory entry:

filter = (&(uid={username})(userPassword={password}))

A non-empty result is treated as a match for that user's directory entry.

3

Session established

On a match, Identra hands your app a session and redirects the user to the authenticated area of your site.

Full configuration keys and supported LDAP directory versions are in the docs.

Why the LDAP bind happens as a service account

Identra never asks the visiting user's browser to talk to LDAP directly. Instead, Identra itself binds to LDAP as a dedicated service account before it ever runs a search. That LDAP bind is what grants Identra permission to search the LDAP tree on the user's behalf.

Once that initial LDAP bind succeeds, the username and password the visitor typed into the login form are substituted into the LDAP filter shown above. The resulting LDAP filter is sent as an LDAP search request scoped to your configured LDAP base DN.

Any LDAP server that returns at least one matching LDAP entry for that filter is treated as confirming the login. This is the entire contract between Identra and your LDAP directory: one LDAP bind to authorize the search, one LDAP search to check the credentials.

What Identra sends to your LDAP server

Every LDAP search Identra issues carries three things: the LDAP base DN you configured, the LDAP filter built from the submitted form fields, and the LDAP service account's existing bind context. Nothing else is required for the LDAP directory to answer.

Because the LDAP filter is assembled directly from the two form fields on the login page, the shape of the LDAP filter is entirely determined by what Identra receives as "username" and "password" — there is no intermediate LDAP query template beyond the one shown above.

Teams migrating from a homegrown LDAP integration usually tell us this is the simplest LDAP auth flow they've deployed: one LDAP bind, one LDAP filter, one LDAP search, and a yes/no answer.
